🔥 The Problem

When an order event needs to travel from a CRM, portal, or internal tool to an ERP, the typical approach creates a fragile system that fails silently.

🔁
Duplicate Processing
Network timeouts and retries cause the same order to be created multiple times in the ERP. No idempotency means every retry is a risk.
📦
Payload Size Limits
Message queues have hard limits (e.g. 64 KB on Azure Service Bus). Large order payloads silently fail or get truncated without any error surfaced to the business.
🌑
No Visibility
When an order disappears, there is no correlation ID, no logs, no status API. Operations teams manually search databases to find what happened.
⛓️
Tight Coupling
Source system (CRM) calls ERP directly. One ERP maintenance window brings down all order submissions. Any ERP API change breaks every source.
💥
Silent Failures
When the ERP is unreachable, orders disappear with no alerting, no retry, no dead-letter queue. The business finds out days later from the customer.
🔐
Security Debt
Connection strings hardcoded in config files, no rate limiting on public endpoints, no audit trail of who sent what and when.
❌ Before — Point-to-point
  • ❌ CRM calls ERP directly over HTTP
  • ❌ Timeout = order lost forever
  • ❌ No correlation ID across services
  • ❌ Duplicate orders on every retry
  • ❌ Status? Call someone in Operations
  • ❌ Any ERP outage = full system down
✅ After — IntegrationHub
  • ✅ Asynchronous pipeline decouples CRM from ERP
  • ✅ Timeout = automatic retry ×3, then dead-letter alert
  • ✅ Every order gets a correlation ID from APIM to ERP
  • ✅ Idempotency guarantees: one order created, always
  • ✅ Real-time status via API and live dashboard
  • ✅ ERP outage = queue buffers orders, no data loss
💡 Our Solution

IntegrationHub is a cloud-native, event-driven integration platform built entirely on Azure PaaS services. It handles the hard problems — reliability, traceability, and security — so source systems only need to POST a single JSON event.

🌐
Single Entry Point
Every source system (CRM, Portal, ERP, manual) sends a single POST /api/events to APIM. One URL, one contract, one subscription key. The pipeline does the rest.
🔄
Fully Asynchronous
APIM returns HTTP 202 Accepted immediately. Order enrichment, queue routing, and ERP delivery happen asynchronously. Source systems are never blocked by downstream latency.
🏗️
Infrastructure as Code
The entire environment — APIM, Logic App, Function App, Service Bus, Storage, Key Vault, App Insights — is deployed from a single Bicep file. Zero manual portal configuration. Repeatable across dev / test / uat / production.
💰
Zero Fixed Cost
Built entirely on Azure Consumption / Serverless tiers. No idle VMs. Scales from zero to millions of orders. Stays within free tier limits for a prototype workload.

⚙️ How It Works

Click each step to see exactly what happens, what data is read/written, and how errors are handled.

1
Client sends an order event
APIM ›
  • What: Any source system sends POST /api/events with an eventId, eventType, sourceSystem, and payload
  • APIM validates: subscription key, rate limit (10 req / 60 s)
  • APIM injects: x-correlation-id header — this GUID tracks the order through every service
  • APIM traces: every request logged to Application Insights automatically
  • Returns: 202 Accepted immediately — client is never blocked
  • Errors: 401 (missing key), 429 (rate limit with Retry-After header)
2
Logic App orchestrates and validates
Logic App ›
  • Schema validation: checks eventId and eventType are present — returns 400 if not
  • Calls: EnrichOrderFunction via HTTP POST with retry policy (3 retries, 10 s interval)
  • On enrichment network failure: posts a webhook alert and returns 503
  • On enrichment success: sends enriched message to Service Bus orders queue
  • Tracked properties: CorrelationId attached to every Logic App action → queryable in Log Analytics
3
EnrichOrderFunction validates and enriches
Function ›
  • Idempotency check: looks for idempotency-store/{eventId} in Blob Storage — if found, silently returns 200 (duplicate discarded)
  • Field validation: eventId, eventType, sourceSystem, payload.productCode, payload.quantity required
  • Enrichment: product description, unit price, total amount, delivery priority (high if qty ≥ 10), routing tag
  • Claim-check: if serialised order > 64 KB, full payload saved to claim-check-payloads/{date}/{id}.json in Blob; only a reference rides the queue
  • Marks processed: writes zero-byte marker blob to idempotency store
  • Returns: enriched EnrichedOrder JSON to Logic App
4
Service Bus queues the enriched order
Service Bus ›
  • Queue: orders queue receives the enriched order
  • Session ID: set to eventId — guarantees FIFO ordering per order
  • Properties: correlationId, eventType, sourceSystem in message metadata
  • Max delivery count: 3 — after 3 failed processing attempts, message moves automatically to Dead Letter Queue (DLQ)
5
OrderProcessingFunction delivers to ERP
Function ›
  • Triggered by: Service Bus message on orders queue
  • Deserialise: JSON fast path; falls back to Base64 decode if needed; logs and rethrows on corrupt data
  • Delivery idempotency: checks delivery:{eventId} marker — if found, recovers "Completed" status and exits (prevents duplicate ERP POST on retry)
  • Status: writes Processing to Table Storage before attempting ERP call
  • ERP HTTP POST: sends correlationId, productCode, quantity, totalAmount, deliveryPriority
  • ERP 2xx: writes Completed to Table Storage, marks delivery idempotency key
  • ERP 4xx/5xx: writes Failed to Table Storage, message completes (not retried — ERP rejected it)
  • Network exception: exception propagates → Service Bus abandons → retries up to 3 times → DLQ
6
Status is queryable at any time
Status API ›
  • Endpoint: GET /api/status/{correlationId} through APIM → StatusFunction
  • Store: Azure Table Storage — PartitionKey = sourceSystem, RowKey = correlationId
  • State machine: null → Processing → Completed or Processing → Failed
  • Response: { status, message, sourceSystem, eventType, lastUpdatedUtc }
  • Live dashboard: auto-polls every 8 s for in-progress orders
7
Dead Letter Queue — nothing is ever lost
DLQ ›
  • Trigger: Timer, runs every 5 minutes
  • Reads: all messages in the orders Dead Letter Queue
  • Logs: each dead-lettered message with its correlationId, reason, and source system
  • Alerts: fires a webhook notification so Operations is immediately aware
  • No data loss: the original message payload is preserved in the DLQ indefinitely until actioned
🛡️ Reliability Guarantees

Every failure scenario has been considered and handled. No order is ever silently dropped.

🔁
Idempotency — at every stage
Two separate idempotency checks prevent duplication:

Enrichment: a zero-byte blob marker per eventId — duplicate submissions are silently accepted (200 OK) without reprocessing.

Delivery: a delivery:{eventId} marker prevents a second ERP POST if the function is retried after a partial success.
Zero duplicate orders
📦
Claim-Check — unlimited payload size
Azure Service Bus has a 64 KB message size limit. IntegrationHub uses the Claim-Check pattern to transparently handle any payload size:

Payloads over 64 KB are offloaded to Blob Storage. The queue message carries only a reference (IsClaimCheck: true). The processing function retrieves the full payload from Blob when needed.
No payload size limits
🔄
Retry → Dead Letter — three layers
Transient failures (network timeouts, ERP downtime) are handled in layers:

Layer 1: Logic App retries the enrichment function 3 times with 10 s intervals.

Layer 2: Service Bus retries delivery to OrderProcessingFunction up to 3 times automatically.

Layer 3: After all retries exhausted, the message moves to the Dead Letter Queue and a timer function fires a webhook alert.
Nothing silently lost
⚡
Decoupled — ERP downtime doesn't break CRM
Because the pipeline is asynchronous and queue-backed, CRM can keep submitting orders even when the ERP is down for maintenance. Orders queue up in Service Bus and are delivered automatically when ERP comes back online.
ERP outage = zero impact on CRM
🚦
Rate limiting — protect downstream systems
APIM enforces a rate limit of 10 requests per 60-second window per subscription key. This protects the entire pipeline from traffic spikes, bot abuse, and runaway client loops. Rate-limited callers receive a 429 with a Retry-After header.
Abuse-resistant by design
📊
Status state machine — always know where an order is
Every order transitions through a defined state machine written to Table Storage in real time:

null → Processing → Completed
null → Processing → Failed

Any client can query the current state at any time via GET /api/status/{correlationId}.
Real-time status for every order

🔒 Security

Designed with zero stored credentials. Every service authenticates via Managed Identity — no passwords, no connection strings in code.

🔑
API Authentication
APIM Subscription Key
Every inbound request must carry a valid Ocp-Apim-Subscription-Key header. Invalid keys are rejected with 401.
🪪
Azure Service Authentication
Managed Identity
Function App and Logic App use System-Assigned Managed Identity with least-privilege RBAC roles. No connection strings in code or config.
🗝️
Secret Management
Azure Key Vault (RBAC)
All secrets (ERP endpoint URL, webhooks) stored in Key Vault. Function App reads via Key Vault references — the secret never touches app configuration directly.
🔒
Transport
HTTPS Only
httpsOnly: true on Function App. APIM configured for HTTPS protocols only. No plain HTTP accepted anywhere in the pipeline.
🗄️
Storage Access
No Public Blob Access
allowBlobPublicAccess: false on the Storage Account. All blob reads/writes go through authenticated Azure SDK calls.
♻️
Data Protection
Soft-Delete Enabled
Key Vault and Blob Storage both have soft-delete enabled (7-day recovery window). Accidental deletions are recoverable.

📋 Prototype → Production

This prototype demonstrates the integration patterns, infrastructure automation, and operational practices of a production-grade system. The following gaps represent the natural next steps before a production go-live.

Gap Priority Production Approach
No OAuth / JWT authentication on APIM High Add Entra ID JWT validation policy — validate audience, issuer, and scopes on every inbound request
Dashboard has no auth High Enable Entra ID Easy Auth on the Function App to require login before the dashboard loads
Single Azure region High Geo-redundant Storage (GRS), paired region failover, Traffic Manager for APIM
Rate limit is global (all callers share one limit) Medium APIM Products with per-caller quotas — separate tiers for CRM, Portal, ERP
No message schema registry Medium Azure Schema Registry with Avro or JSON Schema — enforced governance for all message formats
Webhook URL for failure alerts Medium Azure Monitor alerts + Action Groups → email / Teams / PagerDuty integration
Status table has no data expiry Low Table Storage lifecycle policy to purge rows older than 90 days
ERP endpoint is a flat config value Low API Management backend entity with health probes and circuit breaker policy
No load or chaos testing Low Azure Load Testing (k6) + Azure Chaos Studio to validate retry and DLQ behaviour under real traffic
Single Service Bus queue for all orders Low Separate queues per source system or order priority tier — independent scaling and dead-letter handling
